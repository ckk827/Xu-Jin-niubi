# Windows 内嵌窗口启动修复（2026-11-09）

## 后续：界面卡顿与模型入口

正常 Windows 桌面启动已取消排查阶段保留的 `QT_OPENGL=software` 和 `--disable-gpu`；只有明确的离屏测试保留软件渲染设置。原生窗口检查实际报告 WebGL 可用，渲染器为 NVIDIA RTX 4060 的 ANGLE / Direct3D11，沙箱继续开启。未测量修改前后的帧率，不能将硬件渲染验证等同于所有场景均无卡顿。

导航增加常驻“模型连接”页和桌面顶部“切换模型来源”按钮；连接页直接显示本地模型、外部 API 两个选择。已保存配置仍可修改，不需要重置数据库。房间状态更新和断线重试不会替换打开的模型表单。外部 API 的网址、模型 ID 和密钥分开填写，前后端拒绝把网址当作模型 ID；发现旧配置有此问题时，启动后直接显示连接编辑页。

本次验证：16 项模型连接测试、25 项浏览器检查（业务 9、手机 5、模型配置 11）及原生 Windows 窗口检查通过。模型准备使用模拟接口，不下载模型；外部 HTTP 测试只访问本机模拟服务。

## 原因与证据

本机虚拟环境的 `Scripts/python.exe`、`pythonw.exe` 及 PySide6 运行目录继承了 Windows Low 完整性标记（SID `S-1-16-4096`）。基础 Anaconda Python 为正常 Medium，而由项目虚拟环境启动的 Python 实测为 Low。这会限制临时目录与浏览器启动操作。

Chromium 的 Windows 沙箱会拒绝低完整性可执行映像：最小 HTML 页面也无法加载，渲染器返回 18，详细日志的 `Process.Sandbox.Launch.Error` 为 Windows 错误 5。只修复启动 EXE 后，低完整性 Qt DLL 仍会导致 `0xc0000022`。同时恢复运行 EXE 与 Qt DLL 的正常 Medium 标记（`S-1-16-8192`）后，同一复现程序成功加载并执行 JavaScript。

处理完整性标记后无需升级或降级 PySide6，也无需关闭 Chromium 沙箱。早期关于一般 Qt 兼容性、测试环境不能创建沙箱的判断不够具体；本轮已通过标记修复前后的对照确认原因。

## 处理范围

`soulband-demo/desktop_runtime.ps1` 读取强制完整性标签，只修复指定虚拟环境的 Scripts 目录、Python 启动器、PySide6 目录及其运行映像中的 Low 标记。桌面一键、Demo 和成员入口均在启动 Python 前执行检查。已正常标记的文件不重复修改。

不调整数据库、密钥或用户资料；不增加目录访问授权，不修改 Windows 全局安全设置，不关闭浏览器沙箱或证书校验。诊断阶段临时添加的 Qt 运行库读取授权已撤回，最终修复仅涉及完整性标记。

本机运行环境的标签修复不会通过 Git 传播，因此启动脚本保留检查，供其它环境出现同类问题时使用。现有旧进程不会随文件标签变化恢复权限，需退出旧启动窗口后重新运行 `一键启动宿伴.cmd`。
